# DSH 侧枝会话 — 临时会话 (Side Ask)

[English](./TECHNICAL.md) · **简体中文** · [README](./README.zh-CN.md)

在主会话里选中一段文字，右栏就会打开一条**只读分支子会话**。它继承主会话已有的上下文，逐词流式回答——而**它的答案绝不会进入主会话的模型上下文**。

典型场景：针对当前对话做延伸追问、查词或发散探索，同时不打断主会话的连贯性。

| | |
| --- | --- |
| **包名**（实现） | `dsh-side-branch` |
| **界面显示名** | **临时会话**（英文界面 `Side Ask`） |
| **已验证的 DSH 版本** | `0.1.5-rc.2` 与 `0.1.7-rc.2`（见下文「归档与解锁」） |
| **前置要求** | Node.js ≥ 20，且 `PATH` 上有 `pnpm` |
| **运行时依赖** | 无——零第三方依赖，无构建步骤 |
| **许可证** | MIT |

> **两个名字是刻意的。** 插件叫 `dsh-side-branch`（侧枝会话）；这个功能在**界面里**显示为「**临时会话**」（英文界面 `Side Ask`）——侧栏 tab 标题、面板提示、按钮悬停提示都用这个名字。包名描述实现（只读分支），UI 名描述用途（临时问一句），改名不该动用户已经认得的东西。本页其余部分用「分支」这个词描述它的实现语义。

## 💡 为什么再造一个侧边会话插件？

设计这个项目时（2026 年 3 月），我调研了 DSH 生态里的 14 个侧边会话／气泡类插件，发现**没有一款能同时满足下面全部硬需求**：

1. **真继承上下文**——不是截断后的摘要。
2. **同一段内支持多轮追问**——不是一次性气泡。
3. **逐词流式输出**，包括推理过程。
4. **轻量稳定**——只用官方公开 API，不臃肿。
5. **只读拦在执行层，且绝不破坏前缀缓存**。

当时最接近的几款方案各有取舍，例如：

- [`@michengai/dsh-btw`](https://github.com/MichengAI/dsh-btw) 是一次性旁问：每个问题独立回答，同一话题内无法追问，刷新页面后答案也不再保留。
- [`dsh-side-chat-plus`](https://github.com/heartmove/dsh-side-chat) 默认继承主会话的工具集与权限预设，因此它的侧边聊天是**可写**的——是「第二个 agent 会话」，而不是只读旁问。
- [`dsh-sidenote`](https://github.com/g-yixuan/dsh-sidenote) 是功能完整的侧边聊天，带一键「回流主会话」；按设计它的结论就是要写回主会话的。
- [`@lukeknow0/dsh-side-chat`](https://github.com/Lukeknow0/dsh-side-chat) 架构优秀、只读模型与本插件相近，但其 README 自述仍是 MVP。

最大的分歧点在**「只读」的实现方式**。同类插件普遍在**提示词层**实现：用 `toolFilter` 把工具从提示词里删掉，或用 `tools.restrict` 限制工具。功能上确实达到只读，但代价是侧会话的提示词前缀与主会话分叉，**父会话已经积累的前缀缓存全部失效**，每轮都要重算整个上下文。

本插件把只读拦在**执行层**（`ctx.tools.guard`，`dsh-tools` 的公开契约）：工具仍留在提示词里，模型可以尝试调用，但执行被拒——于是提示词与主会话逐字一致，缓存照旧命中（实测 97%–98%）。

## ✨ 核心特性

- **真分支，零污染。** 宿主半绝不向父会话写入任何内容。你在分支里问过什么、得到什么答案，主会话的模型上下文里都不会出现。
- **继续命中前缀缓存。** 分支出生时读取主会话**已完成回合**的前缀作为种子（每次追问都会重新取一遍——见下文「每轮重建（Re-Fork）」）。沿用主会话模型时，继续命中原有前缀缓存，无需重算提示词。
- **执行层只读隔离。** 安全边界不依赖提示词。由底层 `ctx.tools.guard` 精确放行六个无副作用的查询类工具（`read`、`glob`、`grep`、`web_search`、`web_fetch`、`lsp`），其余一切——写文件、执行命令、开孙子会话——都在执行层被拒。
- **关掉标签也不断的流式输出。** 正文与推理过程逐词推进（推理放在可折叠的「思考」行里）。关闭浏览器标签不会中断后台回答，重新打开结果还在。
- **面板状态会记住。** 按「会话 + 面板格」本地持久化。侧会话闲置后释放活动实例、保留记录，下次提问静默唤醒。

## 📦 安装

任选一种。安装后**必须重启 DSH**——客户端半在启动时装载，只刷新浏览器不够。

从 GitHub 安装：

```powershell
dsh plugin --profile web add github:wucl12/dsh-side-branch
```

从 npm 安装：

```powershell
dsh plugin --profile web add dsh-side-branch
```

从本地目录安装（`link:` 依赖，装的是**指向该目录的链接**，不是快照）：

```powershell
dsh plugin --profile web add C:\path\to\dsh-side-branch
```

> 本地目录安装后，**改了代码就要重新 `add` 一次并重启 DSH**（`lib/client.js` 这类客户端代码只在启动时装载，
> 刷新浏览器不够）。不想重启就改用 GitHub 或 npm 安装。

**路径含空格时**（例如仓库放在 `Documents\` 下），`dsh plugin add` 会把路径拆成两段、装出错误的链接。两个办法，任选一个：

- 把仓库放到不含空格的路径（如 `C:\dev\dsh-side-branch`）再 `add`；或
- **不经过命令行**：在 profile 的 `package.json` 里手写一条依赖，再跑 `install`（路径写在文件里，不会被拆）：

  ```jsonc
  // <DSH_HOME>\profiles\web\package.json
  "dependencies": { "dsh-side-branch": "link:C:/dev/dsh-side-branch" }
  ```

  ```powershell
  dsh plugin --profile web install     # 装完会自动把它加进 dsh.profile.bundles
  ```

把 `web` 换成你实际使用的 profile 名。若 profile 不在默认位置，先设置 `DSH_HOME`。

### 让 agent 帮你装

把下面这段发给任意能执行本机命令的 agent：

```text
请把本机的 DSH 插件 dsh-side-branch 装到 web profile：
1. 确认本机 PATH 上有 pnpm（dsh plugin 是 pnpm 的转发器）；没有就先装。
2. 确认仓库所在目录的绝对路径不含空格。若含空格，改用"不经过命令行"的办法：
   在 <DSH_HOME>\profiles\web\package.json 的 dependencies 里加一行
   "dsh-side-branch": "link:<仓库绝对路径的正斜杠形式>"，然后跑 dsh plugin --profile web install。
3. 不含空格时：dsh plugin --profile web add <仓库绝对路径>
4. 执行 dsh --profile web --dump-config，确认输出里出现 dsh-side-branch 这一行。
5. 告诉我重启 DSH 的命令，然后停在那里等我重启。
```

## 🚀 使用

在主会话正文里选中文字，选区上方出现询问入口。点它打开右栏面板，输入问题并发送——选中的原文会作为引用一起交给分支。

主会话输入框右侧另有一个入口按钮，点它可以直接打开面板（可在设置里关掉）。

面板内的操作：

| 位置 | 作用 |
| --- | --- |
| 输入框 | 提问；同一段内可以继续追问，历史由这段分支自己持有 |
| 底部左侧「清空」 | 结束当前这一段，下次提问另起一段 |
| 底部左侧齿轮 | 打开设置：主会话快速入口按钮的开关 |
| 模型选择行 | 为这一段单独指定模型与推理等级，默认跟随主会话 |

关闭浏览器标签不会中断正在进行的回答；回到面板仍能看到结果。

## 🧭 行为要点

**分支是真分支。** 出生时读取主会话**已完成的回合前缀**作为种子，并继承主会话的 agent preset、工具与 persona。因此这条分支看到的系统提示词与主会话逐字一致。★ **每次追问都会用主会话最新的已结算前缀重建一遍**，同时保留这条分支自己历来的问答（见下文「每轮重建（Re-Fork）」）。

**答案不回流。** 宿主半从不向父会话写入任何内容。你在分支里问过什么、得到什么答案，主会话的模型上下文里都不会出现。

**继续命中前缀缓存。** 因为提示词前缀与主会话逐字一致，沿用主会话模型时仍能命中原有的前缀缓存，而不是每次重算。换成**别的**模型时，供应商侧的缓存是**另一条序列**（前缀再像也算新序列），那一段基本按全价计费，插件会在用量行标注。

**流式输出正文与推理。** 回答逐词推送；推理过程放在可折叠的「思考」行里。客户端断开不会中止后台回答。

**面板状态会记住。** 按「会话 + 面板格」保留，刷新页面不丢。侧会话闲置一段时间后释放活动实例但保留记录，下次提问自动唤醒。

**设置存在浏览器本地。** 官方设置页里看不到本插件的命名空间，这是有意的取舍：改为走官方设置服务需要平台内置包 `schemastery`，插件工作区解析不到它，所以设置改由客户端 `localStorage` 持久化，宿主只做校验。

**归档与解锁：为什么每一轮开跑前都要取消归档。** 侧会话是一条**真实的 DSH 会话**，不处理的话它会作为一行出现在左侧边栏。为了让列表干净，插件在建段那一刻就把它**归档**——归档会把会话从各个分组界面里藏起来，但不删除它。

从 DSH **`0.1.7-rc.1`** 起，已归档的会话同时变成**不可运行**：`dsh-api-session-controller` 组合的 `ArchivedSessionGate` 会在 `agent/pre-step` 上拒掉已归档会话的任何模型步，`dsh-agent-loop` 随即把那一轮收成 `turn/end { reason: 'blocked' }`，**连模型请求都不会发出**。于是"自己归档自己"的插件会每一轮都把自己锁死。

插件的做法是三步循环，每一步都容忍失败：

1. **建段时**归档 —— 空闲的分支不出现在会话列表里；
2. **每轮真的投递之前**（`followup` 之前）调 `workspaceRegistry.unarchiveSession()`，为这一轮解除闸门；
3. **该轮结算后**再归档 —— 空闲的分支重新藏起来。注册表会拒绝归档"仍有活动"的会话，所以这一步按有界退避重试；即使始终失败，唯一后果也只是这段分支留在侧栏可见。

`unarchiveSession()` 是 DSH **`0.1.6-alpha.2`** 才有的方法，调用点做了**特性探测**：在 `0.1.5-rc.2` 上（既没有这个方法、也没有那道闸）第 2、3 步都是空操作，行为与旧版完全一致。这正是同一份发布版本能同时服务两条 DSH 版本线的支点。

## 🔁 每轮重建（Re-Fork）与多段回答

### 一句话规则

每一次追问，发给模型的内容都是：

```text
[ 主会话最新的「已结算前缀」 ]   ← 每次重建都重新取一遍
+ [ 这条分支自己历来的问答 ]      ← 原样重放进去
+ [ 这一轮的新问题 ]
```

「已结算前缀」= 主会话事件里**最后一个 `turn/end` 之前**的全部内容，也就是主会话**答完并收口**的那些回合。主会话**正在生成**的那一轮不进种子。

### 什么时候重建（触发条件）

`shouldReFork` 判两条，**任一成立**就重建：

1. **主会话结算了新的回合** —— 主会话当下的已结算前缀长度 > 这段分支建段时记下的 `parentCut`；
2. **模型或推理等级变了** —— 只改 `reasoningEffort` 也算。

两条都不成立（主会话没长、模型也没换）就**沿用当前这一段**：种子会逐字节相同，重建只会多一条平台删不掉的会话记录和一次深拷贝，缓存命中完全一样。

重建由 `reForkConversation` 执行：新建侧会话（种子 = 主会话**最新**前缀）→ 把上一段分支**自己的**事件重放进去 → 只有**重放成功**才释放上一段。失败时本轮以 `side-branch/refork-failed` **显式拒绝**，**上一段原样保留**（绝不静默降级成"没有历史的新会话"：那会让模型以为这条分支什么都没问过，而面板上还显示着旧答案）。

因为重建会新建侧会话，**`conversationId` 在重建时就会变**；`POST /side-branch/start` 一律回 `handoff: true`，所以面板**不会**画「以下是新的一段」分隔线——历史确实是连续的。

缓存方向的取舍：新增的内容是主会话**刚刚自己请求过**的那一段，很可能还在供应商的热缓存里，重建后的请求前缀正好和它对得上（走缓存读）；而"前缀冻结 + 往后追加"的写法里，同样的内容是这条分支**第一次**以那种形态发出去（走缓存写）。

### 重放的纪律（改代码前先读）

只把**能进模型可见历史的那 5 种事件**原样 `append` 进新会话：

```text
system/message   developer/message   user/message   assistant/message   tool/result
```

- **只传 `event.data` 原样。** `assistant/message` 里嵌着**真实的 provider 流**与 `message.source.provider/model`，手搓一条必被 `dsh-session` 的形状校验拒掉。
- **纯日志事件不重放**（`turn/start`、`step/start`、`tool/call`、`request/header`…）：`append` 它们会抛。
- ⛔ **绝不"顺手补全" `event.sourceEventSeqs`**：`tool/result` 在**事件层**带着 `[旧会话的 callSeq]`，抄过来会撞 `sourceEventSeqs must reference earlier events`（外来序号很可能 ≥ 新会话的 seq）。只传 `data` 天然丢掉它，而它对 `append` 本来就没用。
- **不截断**：到上下文上限就拒绝，不偷偷丢最早的轮次。

### 多段回答：一个 turn 里的多个 step 都要留住

一个 turn 可以含多个 step（"边说边干"），**每个 step 都会开一次新的流式 attempt、各发一个 `start` 帧**。分支保有**有序的段落数组**：

```text
job.segments = [ { kind: 'reasoning'|'text'|'tool', text, turn, step }, … ]
```

- `start` 帧按 `turn`/`step` 分流：**同 step 换 `attemptId`** 才算**同一 step 内重试**（只丢那个 step 已经产出的段落，并发 `reset`）；**`turn`/`step` 变了**才是**新的一段**（发 `segment`，绝不删旧的）。
- `chunk`（`text-delta` / `reasoning-delta`）与 `tool/call` 追加到**当前段**；`assistant/message` 的终局文本**只替换当前段**（而且非空才替换，纯工具收尾的那一步不会把中间输出顶成最终答案）。
- `job.text` / `job.reasoning` 这两个快捷引用是段落数组的**纯函数**（`syncSegmentShortcuts`）⇒ 不可能与段落数组漂移，也不存在"两处真相"。

SSE 事件与载荷完整清单：

| 事件 | 何时发 | 载荷 |
| --- | --- | --- |
| `snapshot` | 客户端（重）连上时先回放一次 | `{ status, text, reasoning, segments, conversationId, stats? }` |
| `segment` | 进入下一个 step（开新段） | `{ turn, step }` |
| `delta` | 正文增量 | `{ text, turn, step }` |
| `reasoning` | 推理增量 | `{ text, turn, step }` |
| `reset` | 同一 step 内重试（只丢该 step 的段落） | `{ turn, step }` |
| `replace` | 终局文本替换**当前段** | `{ text, turn, step }` |
| `tool` | 白名单工具被**执行**（只推工具名，不推参数） | `{ name, count, turn, step }` |
| `done` / `stopped` / `error` | 终态 | `{ status, text, reasoning, segments, conversationId, stats?, error? }` |

客户端把 `segments` 一起落盘（`turn`/`step` 也留着，很小），刷新后按数组顺序渲染；**老数据没有 `segments`** 时由 `answer`/`reasoning` 合成（`normalizeSegments`）⇒ 刷新后老面板不会变空。

### 继承与注入可见（层 1 / 层 2）

- **层 1（每段一行）**：`/start` 回 `synced: { turns, chars }` ⇒ 面板显示「已继承主会话 N 轮 · 约 X 字」。同一轮若真的拼了分支引导词，还会回 `notice`（**注入给模型的引导词全文**，逐字展示，只有每段第一轮才有）。这是本插件注入的**唯一**文本；系统提示词与工具声明是 DSH 自己组装的，**刻意不显示**。
- **层 2（按需展开）**：`GET /side-branch/inherited?conversationId=&locale=` 返回**这一段的切点**（`conv.parentCut`）之前的那些回合，**最后一轮给全文、更早的每轮只给一行摘要**，全在**服务端截断、不调用任何模型**（所以"摘要"不等于"再总结一遍"）。返回里带 `truncated`（有没有被截断）与 `parentHasNewer`（主会话此后又长了 ⇒ 下一轮追问会带上它们）。
- ⛔ **层 2 的内容绝不进面板持久化状态**（`rounds` / `normalizeRound` / `sessionStorage`）：一份主会话前缀可能几十万字符，而面板状态有 5–10 MB 的 `sessionStorage` 配额 ⇒ 塞进去会立刻爆配额、坏掉"刷新不丢"。它只放组件内存态、按需拉一次。

### 上下文上限：改成估算

re-fork 之后**新会话还没有 usage**（老判据 `lastContextTokens` 必然是 `undefined`），所以上限改成估算：

```text
used ≈ 父会话最后一条 assistant/message 的 input + cacheRead + cacheWrite（实测）
     + (分支历史字符数 + 本轮问题字符数) × 安全系数
```

超过 `contextWindow × 0.8` 就**拒绝**并回 `contextFull: { used, limit, window }`；拿不到窗口就按兜底上限。⚠️ **`used` 是估算值**（父前缀那半实测、后半按字符数估），面板上这个数字与该轮结束后的真实用量对不上是正常的。**绝不截断历史**。

### 启动时的孤儿清理与实例租约

re-fork 每次重建都**新增一条会话记录**，而平台的会话持久化层**没有删除会话的 API** ⇒ 记录会无限堆积。所以插件在 `apply()` 时清一次：磁盘上 `sessions/<项目>/side-<uuid>/` 里、**不在本进程账本里**的，就是以前的实例留下的孤儿。

判据必须配**实例租约**才安全：账本在启动时**必然是空的**，所以若同时跑着**第二个共用同一个 `DSH_HOME` 的 DSH 实例**，它启动时会把第一个实例**正在用的**侧枝目录当孤儿删掉（第一个实例内存里还记着它、磁盘日志却没了 ⇒ 那条侧枝直接坏掉）。做法：每个实例启动时在 `<DSH_HOME>/side-branch-instances/` 放一条租约（`<pid>-<uuid>.json`）并定期续心跳，卸载时删掉；清理前只要发现**任何一条还活着的外来租约**就**整个跳过**（心跳过期或进程已死的租约顺手清掉）。

安全校验三条：① 目录名必须**正好**是 `side-<uuid>`（前缀对但形状不对的**不动**、只留痕）；② 不得在本进程的账本里；③ 严格限定在 `sessions` 根目录下、不许路径逃逸。删了什么**逐条记进日志**（平台删不掉，可追溯性只能靠日志）；单条失败只记日志，绝不影响启动。⛔ **不碰**主会话（`session-*`）的任何文件。

## 🛡️ 只读是怎么保证的

只读由**执行层**保证，不依赖提示词请求模型配合。

白名单放行六个工具：

```text
read  glob  grep  web_search  web_fetch  lsp
```

判定按**工具名精确匹配，方向是 fail-closed**。`dsh-tools` 的 `prepareExecution` 对每一次执行都跑一遍 guard，任何不在上面六个名字里的工具都在执行层被拒，包括：

- `subagent`、`workflow`、`ralph` —— 它们能开出孙子会话，而孙子会话的 ctx 上没有我们的 guard；
- `bash`、`pwsh` —— 任意命令；
- `write`、`edit`、`report` —— 写文件；
- `goal`、`jobs`、`cordis` —— 改长期目标、起停后台作业、改运行中的宿主；
- `run_code` —— PTC 模式把动作包进程序执行的通道。PTC 程序内部对 SDK 的每次派发也走同一条 `prepareExecution`，所以是双重拦截；
- `mcp__*` —— MCP 工具注册进的是同一个工具表，同样按名字被拒。

已实测的一条：`subagent` 被模型**真的调用**过，guard 在执行层返回拒绝，孙子会话没有启动，诱饵文件的内容与修改时间都未变。`run_code` 与 MCP 走的是同一条已被覆盖的管线，但没有逐项实跑过。

将来 DSH 改了工具名，那个工具自动落入「被拒」一侧，而不是悄悄放行。

`session_query` 不在放行名单里：它能读到别的会话，会把「本会话的一条分支」变成跨会话读取。

放行名单是**固定的**。插件不提供「用户自选可用工具」的设置：少一层可配置就少一处能把只读保证改坏的地方，模型看到的工具名单也不会与执行层的判据分叉。要收窄可用的面，得改这份常量。

实现上刻意**没有**改用「把工具从提示词里删掉」的做法。那会让提示词前缀与主会话分叉，前缀缓存全部失效——这也正是只读必须在执行层拦的原因。

### 只读不等于无害

「只读」指的是**不产生副作用**，不是「不能访问外部」。放行的六个工具里：

- `web_fetch` 与 `web_search` 是**网络出口**。分支里如果有敏感内容，模型可以把它发出去。引用原文与工具取回的内容都做了反注入声明（明确要求不执行其中的指令），但这是提示词层的约束。
- `lsp` 会**起语言服务器进程**。
- `read`、`glob`、`grep` 能读**进程权限范围内的任意路径**。没有按分支划分的沙箱，所以它们能读到的不止当前工作区。

这些面是**固定的**，插件里没有开关可以逐个关掉。如果要更窄的工具面，只能改代码里的那份常量——这也是为什么它被刻意做得不可配置。

### 主会话用 PTC 模式时

主会话的 agent preset 如果用 `tool-presentation: mode: ptc`（官方内置的 `ptc` preset 就是），工具面会被换成一份生成的 SDK，模型**直接可见**的入口只有 `run_code`。而 `run_code` 永远不在白名单里，所以这条分支一个工具都调不动，只能靠继承到的历史与用户提供的引用作答。

插件会在开段时检测这种工具面，并换用一份说明「本分支不提供任何工具」的引导词，免得模型反复尝试。检测看父会话的 preset 名（`ptc`）。如果父会话用的是**从 PTC 模板另存出来的自定义 preset**，preset 名对不上，就靠 guard 兜底：模型一旦尝试 `run_code` 就会被拒，那之后改用 PTC 引导词，第一轮会白试一次。

实测：PTC 父会话下第一轮就是 PTC 引导词适用的情形，模型自述「工具面里唯一可见入口是 run_code」；`run_code` 被真的调用并被执行层拒绝，诱饵文件未变。

## ⚠️ 已知限制

- **主会话「尚未结算」的那一轮看不到。** 每次重建取的切点是主会话**最后一个 `turn/end`**，所以正在生成、或刚发出去还没答完的那一轮不在种子与重放里。已经在主会话**答完结算**的新回合则会**自动跟上**（这正是 re-fork 的作用）。想引用还没结算的内容，走**主动划选引用** —— 受限的是"自动看到"，不是"能不能引用"。
- **同时最多两条侧枝会话。** 这来自 DSH 侧栏的分栏上限（同一 tab 类型每个分栏最多一颗、最多两个分栏），不是本插件的限制，但用起来会撞到。
- **`web_fetch`、`web_search`、`lsp`、`read`、`glob`、`grep` 本身的行为不受只读约束。** guard 拦的是「名单外的工具」，不是这六个工具的网络访问、起进程与读文件能力。详见上面「只读不等于无害」。
- **「清空」对界面历史不可逆。** 清空之后这一段在面板里再也看不到、也回不去。磁盘上的归档侧会话记录仍在，但官方 API 删不掉它，它也不会出现在任何会话列表里。另外，re-fork **每次重建都会新增一条会话记录**，而平台**没有删除会话的 API** ⇒ 这些记录靠插件**启动时的孤儿清理**回收（见上文）；同一时刻有**两个共用同一个 `DSH_HOME` 的实例**在跑时，清理会**整个跳过**。
- 设置存在浏览器 `localStorage`：换浏览器或清站点数据会回到默认值。目前设置只有一项（主会话快速入口按钮的开关）。
- 工具放行名单不可配置。想收窄可用工具只能改代码，没有针对单个工具的开关。
- 插件重载后，「睡着」的会话表随内存消失，旧会话 id 会报告已另起一段（客户端会自动新建，不会卡住）。
  **注意区分两种路径**：闲置到点只是让侧会话「睡觉」，记录还在，下次提问**静默唤醒**、连分隔线都不出现；只有**插件重载**才会丢记录、另起一段，此时问题照常得到回答、不用重新输入，只是那段历史接不上。
- 每段有上下文上限。到达上限时**拒绝发送**并回 `contextFull: { used, limit, window }`，不会静默丢弃最早的轮次。⚠️ 这个 `used` 是**估算值**（re-fork 之后新会话还没有 usage），不是实测用量。
- **缓存命中率是实测值，不是设计保证。** 平台可能在子会话第一步**原地替换 system 节点**（node 0）——官方原话是 *"A prompt change that replaces a system node in place makes the request differ from that node's first token — in full when the node is node 0"* ⇒ 一旦如此，**从第 0 个 token 起全废**；工具集不一致也会强制开一条新序列。所以不会有"必然命中"这回事，97%–98% 是实测，不是承诺。并且**命中缓存 ≠ 不占上下文窗口**：`inputTokens + cacheRead + cacheWrite` 里命中的那些 token **一样占窗口**。
- 主会话用 `ptc` preset 时，这条分支**一个工具都用不了**（唯一可见入口 `run_code` 永远被拒）。用 PTC 模板另存出来的自定义 preset 还会让开段判定漏判，第一轮白试一次。
- 模型被 guard 拒绝后往往会**再试一次**同一个工具，白花一轮。这与主会话是否 PTC 无关，实测两种模式下都会发生。
- 已在 DSH `0.1.5-rc.2`（尚无归档闸）与 `0.1.7-rc.2`（已有归档闸）上验证。`0.1.6-alpha.2` 只核对了它已发布的包：它已有 `unarchiveSession`、尚未有 `ArchivedSessionGate`，特性探测的分支足以让它照常工作，但**没有在那里跑过端到端**。
- MCP 工具的拦截结论来自代码路径核对，没有实测（`run_code` 已实测）。
- 分支引导词对模型行为的影响没有量化。它要求模型在需要读文件才能得出结论时说明「这需要回主会话做」，是否会让模型过度保守需要人工评判。
